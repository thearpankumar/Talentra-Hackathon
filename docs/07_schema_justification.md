## 1. Engine choice

**Decision (ADR-001):** CockroachDB v26.2 (Regular GA 26.2.0-26.2.6; LTS from v26.2.7, maintenance to 2027-09-23) with the PostgreSQL dialect and wire protocol. The image tag must be pinned to the latest 26.2.x patch after checking Docker Hub (the exact tag is unverified in the research). v26.3 is an Innovation release and is not used.

**Why not the docket's PostgreSQL or MySQL.** The platform target (10M candidate profiles, 1M job requirements, 100M applications, 24x7 audit and notification writes) and the rules that must hold under concurrency (device limits, wallet balance, non-overlap) favour a SERIALIZABLE-by-default distributed engine where random UUID keys and hash-sharded indexes avoid write hotspots. MySQL has no partial indexes, which this design uses 356 times as partial unique indexes (soft-delete naturals, one-open-row rules, device slots). Single-primary PostgreSQL needs sharding middleware beyond one node. Because the docket names PostgreSQL or MySQL, this is recorded as deviation DEV-01 in `08_rule_compliance.xlsx`; CockroachDB is treated as the PostgreSQL family (same dialect, drivers and DDL review).

| Criterion | CockroachDB v26.2 (chosen) | PostgreSQL 16/17 | MySQL 8 |
|---|---|---|---|
| Default isolation | SERIALIZABLE (client retries on 40001) | READ COMMITTED | REPEATABLE READ |
| Horizontal write scale | native ranges, hash-sharded indexes | single primary (Citus/partitions add-on) | single primary |
| Partial unique index (soft delete, one open row) | yes | yes | no (workarounds with generated columns) |
| Exclusion constraints (non-overlap) | **no** (patterns P1-P3) | yes (btree_gist) | no |
| Triggers / RLS | triggers GA in v26.2, RLS GA label unverified; not relied on | yes | triggers only |
| Column-level privileges | **no** (views + table grants) | yes | yes |
| Row-level TTL | yes (background job) | no (cron) | no (events) |
| Licence | CockroachDB Software License; multi-node needs a key (see below) | open source | GPL/commercial |

**Licence caveat (crdb_capabilities.md section 3).** Binaries from 24.3 are under the CockroachDB Software License. Every multi-node self-hosted cluster needs a licence key: Enterprise Free (company plus affiliates revenue below US$10M, own hardware or own public-cloud account, annual renewal, telemetry required), a 30-day Trial, or paid Enterprise. Without a valid key a cluster is throttled to **5 concurrent open SQL transactions** (7-day grace). `cockroach start-single-node` and `cockroach demo` need no licence but are single-node. The 3-node Docker cluster must therefore apply the key right after `cockroach init` and keep outbound telemetry open; Trial may expire mid-project. No feature is verified licence-free, so correctness never depends on triggers, RLS, changefeeds or multi-region (ADR-012, ADR-018).

**Features absent or unverified that the design works around:** exclusion constraints, MERGE (no docs page), `CREATE DOMAIN` (GA only in v26.3), column-level privileges, session advisory locks, `uuid_v7` (not found), DEFERRABLE and NOT VALID foreign keys (unverified), jsonb `?` index acceleration (unverified), SKIP LOCKED under SERIALIZABLE (gated), custom session variables such as `SET app.user_id` (unverified). Patterns P1-P6, D-13 and D-14 (04_design_conventions.xlsx, Patterns sheet) replace them.

**Portability to stock PostgreSQL (exit path):** drop `USING HASH ... WITH (bucket_count)` (plain btree), replace row-level TTL by cron deletes, rename identifiers longer than 63 characters (203 names, DEV-06; CockroachDB itself allows 128 bytes, `max_identifier_length`, crdb_capabilities row 22, so no change is needed on this engine and the lint only reports it as a deviation, never an error), change STRING(n) to varchar(n)/text, remove STORING (use INCLUDE) and re-test the CHECKs that use `~`, jsonb `?` and num_nonnulls. No CockroachDB-only semantics are needed for correctness.

## 2. Key type

Every one of the 1306 tables has `id UUID NOT NULL DEFAULT gen_random_uuid()` as primary key (ADR-002, check N04 in `08_rule_compliance.xlsx`); all 2951 foreign keys are UUID. No sequences, no SERIAL. Reasons: CockroachDB documentation recommends UUIDv4 to spread writes across ranges; `uuid_v7()` is not available; sequential keys hotspot; keys carry no information so they are safe in URLs. Cost: 16-byte keys enlarge 2271 secondary indexes and 2951 FK columns, and the keys carry no time order, so every time-ordered read uses a timestamp column behind one of the 189 hash-sharded indexes (ADR-003; bucket_count 8: 34, 16: 117, 32: 38). Natural keys (email, GSTIN blind index, external reference, lookup code) are UNIQUE constraints or partial unique indexes. Gapless business numbers use a locked counter row (`invoice_number_series`, BR-SUB-12), not keys. The only non-random ids are `dim_date` and `dim_time_of_day` (UUIDv5, DEV-08).

## 4. Module-by-module justification

Each subsection gives the computed size, why the entity set looks like this, the competitor comparison taken from the module notes and the module's own deviations. Table names are real.

### 4.1 `master_data` (Master data; docket module)

**Size (computed):** 70 tables (28 entities + 42 lookups), 752 columns, 76 FKs, 0 soft / 70 hard / 0 append-only, 0 hash-sharded indexes, 0 TTL tables, 0 views, 18 business rules, Sensitive 0 / Personal 0 columns, 64 nullable columns.

**Entity set.** Shared reference data for every other module: geography (`country`, `state_region`, `city`, `locality`, `postal_code`, `time_zone`), language/i18n (`language`, `ui_label`, `ui_label_translation`), `currency`, the skill graph (`skill_category`, `skill`, `skill_alias`, `skill_relation`), education (`qualification`, `field_of_study`, `institution`, `institution_alias`), industry (`industry` + `industry_closure`), roles (`job_category`, `job_role`, `job_role_alias`, `job_role_skill`), employer dedupe (`employer_name_canonical`, `employer_name_alias`) and `tax_id_type`.

**Why this design.** Free text from users must map to canonical rows or search, matching and analytics fragment. A table is a lookup when it is a small closed set that drives behaviour and has only code/name/order/active; it is a rich master when rows carry hierarchy, attributes or volume (country, city, skill...). Everything is hard-delete-free: rows are retired with `is_active` or merged via a `merged_into_*_id` pointer because millions of history rows reference them (FK RESTRICT). `tax_id_type` stores per-country regex, length, checksum and mask so GSTIN/PAN/CIN/TAN, EIN, VAT etc. are validated before hashing.

**Competitor comparison.** LinkedIn (about 39-41k skills, 26 languages, about 374k aliases, over 200k skill-to-skill links, 26 job functions, about 400 industries): structure matched by `skill`/`skill_alias`/`skill_relation`/`language`/`industry`; seed volumes are targets, not loaded. Naukri (functional area/role/industry tree, notice-period buckets, city tier, engagement type) matched; Monster/Indeed (job type, salary period, shift) matched. Exceeds with multilingual aliases, closure table, canonical employers/institutions, per-country tax-id validation and reason-code lookups. Deliberately omitted: religion, caste, disability, ethnicity and nationality-of-origin masters (legal risk).

**Module-specific deviations and trade-offs.** Hindi translations exist for only part of the lookups (see gap G-24); fallback cycles cannot be CHECKed in CockroachDB (nightly job BR-MST-04).

### 4.2 `profile` (Profile; docket module)

**Size (computed):** 90 tables (52 entities + 38 lookups), 1138 columns, 206 FKs, 28 soft / 58 hard / 4 append-only, 5 hash-sharded indexes, 4 TTL tables, 2 views, 33 business rules, Sensitive 6 / Personal 49 columns, 288 nullable columns.

**Entity set.** Candidate identity and contact (`candidate_profile`, `candidate_contact_phone`, `candidate_contact_email`, `candidate_address`, `candidate_identity_verification`), core sections (`candidate_education`, `candidate_experience`, `candidate_skill`, `candidate_language`, `candidate_project`), LinkedIn/Naukri depth (`candidate_certification`, `candidate_award`, `candidate_patent`, `candidate_publication`, `candidate_volunteer_experience`, `candidate_recommendation`, `candidate_skill_endorsement`, `candidate_follow`), preferences (`candidate_job_preference` plus five `candidate_preferred_*` bridges, `candidate_work_authorisation`, `candidate_open_to_work_signal`), documents (`resume`, `resume_template`, `resume_parse_result`, `candidate_media_file`, `profile_import`), scoring and learning (`profile_completion_rule`, `assessment`, `course_enrolment`), history (`candidate_profile_view`, `candidate_activity_log`, `candidate_shortlist_item`, `candidate_shortlist_history`) and growth/compliance (`referral`, `referral_reward`, `candidate_erasure_request`).

**Why this design.** One profile per user (`uq_candidate_profile_app_user_id`); national id never stored (`candidate_identity_verification` keeps `vendor_token` and a keyed HMAC `id_number_hmac`); salary amounts nullable with a disclosure lookup (D-09); special-category data isolated in `candidate_diversity_declaration`; resumes form a version chain with one default per profile and a scan status gate; views/activity/shortlist history are append-only, hash-sharded and TTL-expired; shortlist items are tenant-pinned by a composite FK to `candidate_shortlist_folder`. Erasure is anonymise-in-place with `candidate_erasure_request` as evidence (ADR-026). Legacy sync idempotency via `legacy_candidate_ref` and `profile_import`.

**Competitor comparison.** LinkedIn: certifications, honours, patents, publications, volunteering, section ordering, endorsements, recommendations, follows, open-to-work all modelled; exceeds with assessment-verified skills, disclosure-aware salary, per-country work authorisation and erasure evidence; groups/newsletters moved to ext_network. Naukri: all headline fields matched, exceeds with resume version chain, scan status and parse provenance. Monster: multiple resumes, visibility per resume, work authorisation matched; security clearance not first-class (G-04). Indeed: privacy and availability matched.

**Module-specific deviations and trade-offs.** Contact phone/email are mirrored on `candidate_profile` for card speed (BR-PRF-04, nightly drift job); resume text is the only unbounded Personal body and is encrypted at the storage layer; free text carries a nullable `language_id` where the language may be unknown (former finding F-06, resolved).

### 4.3 `jobs_applications` (Jobs and Applications; docket module)

**Size (computed):** 99 tables (57 entities + 42 lookups), 1171 columns, 213 FKs, 28 soft / 60 hard / 11 append-only, 14 hash-sharded indexes, 4 TTL tables, 3 views, 33 business rules, Sensitive 1 / Personal 27 columns, 244 nullable columns.

**Entity set.** Requirement header `job_requirement` with per-slot `job_position`, normalised children (`job_requirement_skill`, `job_requirement_location`, `job_requirement_qualification`, `job_requirement_benefit`, `job_requirement_screening`), counters split into `job_requirement_stat`, pipeline (`job_application`, `application_status_transition`, `job_application_status_history`, `application_note`, `application_scorecard`), interviews (`interview` and 5 children), offers (`offer`, `offer_revision`, `offer_approval`), `joining`, `rejection`, candidate-side history (`candidate_job_search_history`, `job_view_event`, `job_bookmark`) and reach (`job_posting_channel`, `job_syndication`, `job_share_event`, `job_boost`, `talent_pool`, `job_walk_in_session`).

**Why this design.** Status transitions live in the database: a history row has a composite FK to `application_status_transition` and a self composite FK chain (application, prior sequence, from status) makes the chain gap-free; one live application per candidate and requirement via a partial unique index; questionnaire integrity via a composite FK chain; tenant isolation by `organisation_id` plus composite FK to `job_requirement` (D-11); salary semantics with `salary_disclosure_id`. Search uses a STORED `title_search` with trigram GIN plus an external engine (D-16). `job_application` (about 100M rows at full scale) leads every secondary index with ids; only `applied_at` and `status_changed_at` are hash-sharded (bucket_count 32).

**Competitor comparison.** LinkedIn posting/Talent (workplace type, screening questions, pipeline, rating) covered; InMail credits live elsewhere. Naukri RMS (walk-ins, CTC not disclosed, hot vacancy, consultant postings, folders) covered. Monster/Indeed (benefit chips, knock-out screeners, sponsored jobs, syndication, reporting) covered. Greenhouse Harvest (applications, scorecards, interviews, offers, approvals, openings, close reasons) covered except demographic data. Exceeds with tenant-safe composite FKs, a status chain and offer revisions.

**Module-specific deviations and trade-offs.** The partial unique predicate cannot reference the status lookup, so withdrawal is a column (`withdrawn_at`) mirrored by the status; `vw_recruiter_job_requirement` has a single definition with an explicit viewer argument (former finding F-02, resolved); long index names (DEV-06).

### 4.4 `administration` (Administration; docket module)

**Size (computed):** 88 tables (46 entities + 42 lookups), 1017 columns, 163 FKs, 10 soft / 69 hard / 9 append-only, 7 hash-sharded indexes, 6 TTL tables, 5 views, 30 business rules, Sensitive 8 / Personal 20 columns, 177 nullable columns.

**Entity set.** Identity (`app_user`, `user_status_history`), authorisation (`app_role`, `permission`, `app_role_permission`, `app_user_role`, `app_role_inheritance`, `app_role_eligibility`), secrets (`user_credential`, `mfa_factor`, `password_reset_token`, `identity_session`, `api_key`), consent (`consent_document`, `user_consent`), audit tier (`audit_event`, `audit_chain_head`, `audit_chain_checkpoint`, `error_log`, `security_event`), blocking (`user_block`, `organisation_block`) and governance (`data_subject_request`, `data_retention_policy`, `purge_job_run`, `legal_hold`, `privileged_access_request`, `impersonation_session`, `moderation_case`, `user_merge_request`).

**Why this design.** One identity table with an immutable actor type and role rows; recruiters cannot register candidates because a composite FK to `registration_policy` has no (candidate, recruiter, *) row; privileges are enforced in four layers (DB roles with REVOKE, views as row security, constraints, application data scope); audit is append-only with 32 parallel hash chains, signed checkpoints and a changefeed to an immutable sink (ADR-013); credentials argon2id with per-row parameters; blocks are effective-dated and read through `vw_candidate_visible_to_user` (ADR-039).

**Competitor comparison.** LinkedIn member block (mutual invisibility), company page admin roles, DSAR audit: matched, with effective-dated reasoned blocks and a DSR SLA table beyond them. Naukri 'block companies' and recruiter sub-users: company blocks first class, sub-users deferred (section 10). Industry IAM practice (hashed tokens, refresh-token rotation with reuse detection, break-glass) modelled.

**Module-specific deviations and trade-offs.** Audit columns on business tables are not FKs (DEV-02); `audit_event.entity_ref` and similar are FK-less (DEV-09); TTL on `audit_event` is compatible with its children because their FKs are ON DELETE SET NULL (F-01, resolved); role-name inconsistency with the analytics module (F-08).

### 4.5 `organisation_account` (Organisation and account; docket module)

**Size (computed):** 65 tables (38 entities + 27 lookups), 801 columns, 141 FKs, 20 soft / 40 hard / 5 append-only, 2 hash-sharded indexes, 1 TTL tables, 4 views, 25 business rules, Sensitive 7 / Personal 29 columns, 193 nullable columns.

**Entity set.** Tenant `organisation`, `organisation_location`, commercial `account` with `account_organisation` and `account_admin`, effective-dated `recruiter_organisation_mapping`, tree (`organisation_hierarchy`, `organisation_hierarchy_closure`, `organisation_hierarchy_change`), compliance (`organisation_identifier`, `organisation_verification`, `organisation_document`, `organisation_domain`), page content (`organisation_media`, `organisation_benefit`, `organisation_brand`, `organisation_career_page`), reviews (`organisation_review` family and `organisation_rating_summary`), data quality (`organisation_alias`, `organisation_merge`) and commercial (`client_relationship`, `organisation_invitation`).

**Why this design.** Recruiter mapping is the single owner of 'which recruiter may act for which company' and uses P1 + P3 (ADR-009); the hierarchy prevents cycles by a level-increment composite FK (ADR-010); tax ids are encrypted with an HMAC blind index so one GSTIN/EIN/VAT cannot be claimed by two companies; verification keeps vendor status and idempotency key and never silently flips to verified when the vendor is down; follower counts are not stored (hot-row contention).

**Competitor comparison.** LinkedIn Company Page (name, tagline, industry, size, HQ, verified badge, admins, followers) covered; Naukri/Monster employer profile (GST/CIN, recruiter list, career page, perks) covered; Glassdoor/AmbitionBox style reviews covered. Beyond them: parent/ultimate-parent hierarchy with ownership percentage, staffing client contracts, merge workflow. Falls short deliberately: employee graph and salary data (Tier 3).

**Module-specific deviations and trade-offs.** 'At least one active admin' is a counter plus CHECK maintained under FOR UPDATE (`vw_account_active_admin`); `helpful_count` is a batch counter; sub-roles deferred with a concrete extension design (section 10).

### 4.6 `gig_marketplace` (Gig marketplace; docket module)

**Size (computed):** 65 tables (34 entities + 31 lookups), 803 columns, 129 FKs, 22 soft / 38 hard / 5 append-only, 7 hash-sharded indexes, 2 TTL tables, 3 views, 27 business rules, Sensitive 1 / Personal 21 columns, 164 nullable columns.

**Entity set.** Worker side (`gig_worker_profile`, `gig_worker_skill`, `gig_worker_certification`, `gig_service_offering`, `gig_service_package`, `gig_availability_rule`, `gig_availability_window`, `gig_time_off`), demand side (`gig_request`, `gig_request_milestone`, `gig_request_status_history`), matching (`gig_application`, `gig_invite`, `gig_assignment`, `gig_slot`, `gig_requester_worker_list`), outcomes (`gig_rating`, `gig_worker_rating_summary`, `gig_dispute`, `gig_cancellation`), money and fulfilment (`gig_timesheet_entry`, `gig_payout_reference`, `gig_earnings_snapshot`, `gig_fulfilment_event`, `gig_fulfilment_event_attempt`).

**Why this design.** A separate subsystem rather than a job variant (ADR-005). Overlap rule B35 by P2: assignment windows on a 15-minute grid are exploded into `gig_slot` rows with UNIQUE (`gig_worker_profile_id`, `slot_start_at`); time off uses the same table so leave and work cannot overlap. Price consistency, accepted-application chain, rating-only-when-completed and favourite-xor-blacklist are composite FKs and partial uniques; external fulfilment is idempotent (handoff key, webhook key) and earnings are reconciled copies, never the source of truth.

**Competitor comparison.** Upwork (milestones vs hourly diary, ratings, availability) covered except connects pricing and escrow; Fiverr (packages, revisions) covered except seller levels; TaskRabbit, Uber, Urban Company (rate, radius, favourites, KYC with document expiry, ratings) covered; Toptal vetting tiers via `verification_status`; Freelancer contests not modelled.

**Module-specific deviations and trade-offs.** `gig_slot` has no updated_* columns (DEV-03); very-high volume (~40M slot rows) with 90-day TTL and hash-sharded slot time; cross-type reporting needs `vw_unified_demand`.

### 4.7 `licences_devices` (Licences, seats, devices and sessions; docket module)

**Size (computed):** 34 tables (19 entities + 15 lookups), 385 columns, 71 FKs, 6 soft / 21 hard / 7 append-only, 7 hash-sharded indexes, 4 TTL tables, 3 views, 16 business rules, Sensitive 4 / Personal 10 columns, 60 nullable columns.

**Entity set.** `licence` (max_users, max_devices_per_user), `licence_seat_slot`, `licence_seat`, `licence_user_invitation`, `licence_transfer`, `licence_ip_allowlist`, `device`, `device_slot`, `device_session`, `session_activity_sample`, `login_attempt`, `device_revocation`, `session_revocation`, `device_limit_violation`, `device_trust_challenge`, `push_registration`, `licence_usage_snapshot`, `licence_status_history`.

**Why this design.** Two-level slot model (ADR-008): `licence_seat_slot` pre-creates slots 1..max_users and `device_slot` pre-creates 1..max_devices_per_user per seat; an active `device_session` claims a slot through the partial unique `uq_device_session_device_slot_id` (WHERE ended_at IS NULL); login locks only that user's `licence_seat` row. A session counts iff `ended_at IS NULL`; expiry is released lazily at login and by a one-minute job; revocation and breach write audit rows. Device fingerprints are HMACs only; login history is a view over `login_attempt`.

**Competitor comparison.** Microsoft 365 / Slack / LinkedIn Recruiter (named seat assignment with reassignment history) matched by seat + transfer + invitation; Netflix / Okta (device or session cap with sign-out-oldest) matched by `device_limit_policy` (deny_new or replace_oldest).

**Module-specific deviations and trade-offs.** Locks are best-effort under SERIALIZABLE, hence retries and the declarative slot twin; TTL vs children resolved (F-01): the FKs from `session_revocation`, `device_limit_violation`, `profile_download` to `device_session` are ON DELETE SET NULL and `session_activity_sample` cascades; an FK cycle with `identity_session` is broken by a nullable `device_session_id`.

### 4.8 `sourcing_consultant` (Sourcing and consultant requests; docket module)

**Size (computed):** 42 tables (27 entities + 15 lookups), 476 columns, 102 FKs, 14 soft / 20 hard / 8 append-only, 10 hash-sharded indexes, 5 TTL tables, 3 views, 16 business rules, Sensitive 0 / Personal 10 columns, 91 nullable columns.

**Entity set.** Consultant side (`consultant_profile`, `consultant_specialisation`, `consultant_desk`, `consultant_job_openness`, `sourcing_request`, `sourcing_request_decision`, `sourcing_shortlist`, `sourcing_submission`, `sourcing_commission`, `consultant_rating`) and recruiter tooling (`outreach_template`, `outreach_batch`, `outreach_recipient`, `outreach_exclusion`, `outreach_message`, `outreach_reply`, `outreach_credit_usage`, `saved_search`, `candidate_search_history`, `candidate_note`, `candidate_tag`, `candidate_contact_attempt`).

**Why this design.** 'A consultant may act only on requirements open to consultants' has no cross-table CHECK in CockroachDB, so openness rows are created under a FOR UPDATE check of `job_requirement.is_open_to_consultants`, `sourcing_request` carries a composite FK to its own requirement's openness row, and consultant identity is bound by a composite FK; closing the flag closes openness rows in the same transaction (BR-SRC-02). Blocks bind outreach (`INSERT ... SELECT ... WHERE NOT EXISTS`, `outreach_exclusion`). Credits reserve, consume, refund on reply through the wallet ledger.

**Competitor comparison.** LinkedIn Recruiter (projects, saved searches with alerts, InMail credits with reply refund, notes/tags, templates), Naukri RESDEX (search history, mailers, folders) and Monster talent pools covered.

**Module-specific deviations and trade-offs.** The openness-iff-flag link is transactional (documented residual risk); message bodies retained 90 days (TTL), replies 180 days, search history 24 months; recruiters never create candidate rows.

### 4.9 `subscriptions_payments` (Subscriptions, wallet, payments and download history; docket module)

**Size (computed):** 74 tables (39 entities + 35 lookups), 879 columns, 165 FKs, 17 soft / 49 hard / 8 append-only, 9 hash-sharded indexes, 1 TTL tables, 4 views, 30 business rules, Sensitive 5 / Personal 7 columns, 151 nullable columns.

## 6. Extension modules and Tier 3: decision record

**Context.** The docket defines 11 modules (Tier 1 and 2 domains) and lists Tier 3 (salary benchmarks, company ratings, trending job snapshots, dashboard aggregates, feature flags) as optional stretch coverage that must be a separate, clearly labelled module with the decision recorded. The scope was widened by the team to a full LinkedIn/Naukri-class product suite, which the docket neither requires nor forbids; it scores depth and competitor coverage.

**Decisions.**

1. Tier 3 is TAKEN ON as `tier3_reference` (24 tables), physically separate: no Tier 1/2 or analytics table references it (computed: 0 FKs from the 11 docket modules into it); only two extension FKs point in (`article_salary_benchmark`, `ab_experiment`). It implements the Section 6 boundary 'Company review and salary data' (reference only, attribution and refresh date) and demonstrates feature-flag design. Risk: stale reference data (mitigated by `reference_data_source.max_staleness_days`).
2. Five EXTENSION modules are added, all labelled tier X and prefixed by purpose in the dictionary: `ext_network` (88 tables), `ext_matching` (78), `ext_ads` (79), `ext_learning` (112), `ext_talent_ops` (125): 482 tables, 37% of the schema.
3. Independence is verified, not asserted: computed foreign keys from non-extension modules into extension modules = 0; extension-to-extension foreign keys across different extension modules = 0; extension-to-core foreign keys = 549 (e.g. `connection` references `app_user`). Dropping an extension module therefore needs no change to core tables.
4. Extensions reuse rather than duplicate: connections reuse `user_block`, `community_follow`, `candidate_skill_endorsement`, `payment_order`; ads settle through `wallet_ledger_entry`; learning reuses profile's `course`/`assessment`; talent_ops reuses `moderation_case`, `user_consent`, `candidate_profile`. They invent no new money, consent or audit mechanism.
5. Extensions obey every Section 5 rule (same lint, same conventions) and carry their own business rules (ext_network 32, ext_matching 22, ext_ads 25, ext_learning 32, ext_talent_ops 42).

**Trade-offs and risks.** Review effort and DDL size grow; extension tables are not seeded or measured at scale (gap G-26); several are very high volume (connections about 2.5B rows, impressions, answers, events) and their performance claims are design-only; the 2-day hackathon scope makes depth in the core modules the priority. The panel can score the 11 docket modules independently because the extension modules are separable.

**Alternatives rejected:** staying at the 11 modules (loses the competitor-coverage argument); folding extension tables into core modules (loses separability and review clarity).

## 10. Sub-roles inside an employer organisation (out of scope now; extension path)

The docket explicitly excludes separate posting, interviewing and pipeline roles inside an employer organisation for this version and asks how the design would be extended. **Today:** an organisation has account administrators (`account_admin`, account scope), mapped recruiters (`recruiter_organisation_mapping`, effective-dated, all jobs of the mapped organisation or its descendants through `organisation_hierarchy_closure`) and platform roles from administration (`app_role`, `app_user_role` with organisation scope, `app_role_permission` with data scope). Every mapped recruiter has the same rights on all of the organisation's requirements.

**How sub-roles would be added without changing existing tables:**

1. Roles as data: insert new `app_role` rows (poster, interviewer, pipeline_manager, viewer; organisation-scoped), their `app_role_permission` rows with data scope `organisation` or `assigned_requirement`, and `app_role_eligibility` rows; express 'pipeline manager includes interviewer' with `app_role_inheritance`.
2. Membership: add the proposed table organisation_member_role (organisation_id, app_user_id, org role lookup, optional `organisation_department` scope, effective_from/effective_to) with the same P1 chain and P3 open-row constraints used by `recruiter_organisation_mapping`, so memberships cannot overlap.
3. Per-requirement assignment: add the proposed table job_requirement_member (job_requirement_id, app_user_id, app_role_id) beside the existing `job_requirement_assignment` (tenant-pinned by composite FK like other children).
4. Enforcement: extend `vw_recruiter_job_requirement` and `vw_user_effective_permission` with an EXISTS over the membership table; permissions keep their `enforcement_layer` and audit flag; high-risk actions use the existing four-eyes table `admin_action_approval`.
5. Seat-level roles (seat admin vs member) can use a new seat-role column on `licence_seat`; ad accounts already have `ad_account_member` for their own roles. No change to `job_requirement`, `job_application` or `organisation` is needed; analytics adds an attribute to `dim_user` and a bridge.

This path is recorded as ADR-034.

## 12. Deviations from the dictionary and overrides applied by the build (infra/schema)

The DDL under `infra/schema` is generated from the dictionary; the items below are where the deployed schema differs from, or adds to, the dictionary text. Each is also listed in `docs/21_alignment_report.md`.

1. **View overrides (29).** The dictionary `sql_sketch` of these views was replaced by a hand-written definition in `infra/schema/parts/views/<name>.sql` because the sketch used constructs the engine rejects or returned wrong rows: `mv_kpi_summary_monthly`, `mv_wallet_cover_risk`, `vw_ad_campaign_report`, `vw_assessment_item_statistics`, `vw_candidate_job_recommendation_live`, `vw_candidate_learning_transcript`, `vw_candidate_profile_recruiter`, `vw_candidate_visible_to_user`, `vw_certificate_public_verification`, `vw_consultant_job_requirement`, `vw_consultant_open_requirement`, `vw_course_catalogue_public`, `vw_dim_candidate_current`, `vw_drive_funnel`, `vw_employer_learning_compliance`, `vw_gig_open_request`, `vw_gig_worker_public`, `vw_learning_leaderboard_latest`, `vw_live_job_requirement`, `vw_mentor_directory`, `vw_onboarding_progress`, `vw_outreach_eligible_candidate`, `vw_raw_title_review_queue`, `vw_recommendation_ctr_hourly`, `vw_recruiter_searchable_candidate`, `vw_salary_benchmark_published`, `vw_sponsored_job_serving`, `vw_unified_demand`, `vw_upcoming_event`.

2. **BR-LRN-07 fix.** The rule "at most one current price per course, market and access model" had no enforcing index; the unique partial index `uq_course_list_price_course_id_country_id_course_access_model_id_current` (WHERE valid_to IS NULL AND deleted_at IS NULL) was added in `docs/_staging/ext_learning.yaml`, so the DDL and the dictionary agree.

3. **Dialect limitations.** The CockroachDB PL/pgSQL dialect has no FOUND, no RECORD variables, no FOR loops over queries, no PERFORM and no GET DIAGNOSTICS. Rules that needed them are implemented as triggers or set-based statements (single INSERT ... SELECT / UPDATE ... RETURNING) instead of procedural loops; behaviour is the same, and the mechanism label in `06_business_rules.xlsx` is the contract.

4. **Restore loses grants.** RESTORE does not bring back explicit grants, non-root owners or default privileges (verified on v26.2.8). The backup handler mirrors roles, memberships, owners and grants from the main cluster after every restore (the sync acl step). Default privileges and function EXECUTE grants are not mirrored; they return when `infra/schema/apply.py` is re-run against the backup copy.

5. **Sync restores under a stable name.** The earlier design (restore under a temporary name, then rename-swap with the old copy) cannot work once views exist: RESTORE rewrites view definitions to the new database name and ALTER DATABASE RENAME then fails with a dependency error. The sync therefore drops the old copy and restores under the stable name; the backup copy is briefly absent during a restore.

6. **Rename swap with views is impossible.** The same limitation means no rename-based database or table swap is offered for objects that views depend on; schema change is by idempotent re-apply (CREATE OR REPLACE, IF NOT EXISTS).

7. **Licence.** CockroachDB v26.2 has no Core edition; an unlicensed multi-node cluster is throttled after a 7-day grace period. The stack applies an Enterprise Free key from CRDB_LICENSE_KEY and CRDB_ORG at bootstrap. Backup encryption options and some Enterprise-tier features remain **unverified** against the licence terms (see `docs/15_security_design_note.md`).
