## 1. Security architecture in one page

* **Zones:** (1) edge (CDN/WAF/API gateway), (2) application tier with separate pools per persona and per service, (3) CockroachDB cluster (3 nodes, TLS, certificate-authenticated logins), (4) KMS and secrets vault, (5) object storage for backups, change-feed sinks (audit, ledger) and uploads, (6) a separate backup cluster used only for restores.
* **Principles:** default deny; least privilege per tier; the database enforces what it can declaratively (composite FKs, partial unique indexes, CHECKs, slot tables), views carry visibility predicates, the application layer carries the rest and is tested (B79); sensitive values are never stored in clear (hash, ciphertext, vendor token); evidence is append-only and tamper-evident; nothing the database stores can be turned back into a secret without a key held outside it.
* **What CockroachDB does not give us** (and how the design copes): no column-level GRANT (views and separate tables instead), RLS and triggers are optional hardening only, no SECURITY DEFINER guarantee, owner/admin bypass REVOKE (ownership parked on a NOLOGIN role), no `encrypt()/decrypt()` without an enterprise/CCL note (application-layer AES-GCM instead), change feeds and backups ignore views and RLS (authority is the query-time view).
* **Docket mapping:** Rule group 6 (classification) -> section 2 and sheet `SensitiveColumns`; Rule group 4 (audit, retention) -> sections 10 and 12; Rule group 9 (licence/devices/sessions) -> section 8; Rule group 10 (ledgers append-only) -> sections 9 and 10; section 3 (actors) -> `13_rbac_matrix.xlsx`; section 6 (boundaries) -> section 16.

## 3. Encryption in transit

* **Cluster:** secure mode only (`--certs-dir`; `--insecure` is for throw-away local development and is never used for the seeded database). Private CA created once with `cockroach cert create-ca` (key kept offline, 10-year validity); node certificates `cockroach cert create-node <hostnames>` (1-year validity, SANs for every address clients and nodes use); client certificates `cockroach cert create-client <user>` per service/persona login (90-day validity, CN = user name). Rotation by replacing certificate files and reloading the node (CockroachDB reloads certificates on SIGHUP; verify on the image) before expiry, with an alert at 30 days (`seconds_until_...` metrics and an expiry-scan job).
* **Authentication:** service logins use `PASSWORD NULL` (certificate only) and host-based authentication rules restricting source networks (`server.host_based_authentication.configuration`); no password logins from the internet; no shared accounts.
* **Clients:** `sslmode=verify-full`, TLS 1.2 minimum (1.3 where the driver supports it); connection strings never carry passwords.
* **Edge and providers:** TLS 1.2+ on all public endpoints with HSTS; webhooks verified by signature; outbound calls to vendors over TLS with certificate validation, optionally mTLS.
* **As deployed by `infra/` (accepted deviations for the current stage):** the compose stacks use the CockroachDB internal CA with `sslmode=verify-full` and password login (SCRAM-SHA-256, minimum length 12) for the infra login users; certificate-only logins and `server.host_based_authentication.configuration` are not configured yet (the DB ports are restricted to the owner IP by the EC2 security group). Node and root client certificates are issued for 5 years (the CA for 10), not 1 year / 90 days, and the infra README shows connection strings that carry a password; rotation to the periods above and per-service client certificates are deferred to production hardening. The cluster TLS minimum is the CockroachDB default (TLS 1.2) and Caddy sends HSTS on the public hostnames. Certificate and licence expiry alerts are in `infra/monitoring/prometheus/rules/20-alerts-cockroachdb.yml`.
* **Test:** AT-38 (insecure, unknown CA and expired certificate are refused).

## 5. Field-level protection designs

### 5.1 Envelope encryption (AES-256-GCM)
* **Format** (BYTES): `version(1) | key_version(2) | nonce(12) | ciphertext | tag(16)`; random 96-bit nonce per encryption; **AAD** = `table_name || column_name || row id` so a ciphertext cannot be moved to another row or column.
* **Keys:** a KMS key encryption key (KEK) per purpose wraps data encryption keys (DEKs). Patterns used by the model: per-tenant DEK (`organisation_identifier`, `key_version`), per-row DEK (`candidate_diversity_declaration`, wrapped DEK carried in the envelope header), per-thread DEK (`message`), per-factor DEK (`mfa_factor.encryption_key_ref`). DEKs are cached in service memory for minutes, never logged, never stored unwrapped.
* **Decrypt authority:** only `auth_svc` (MFA secrets), `compliance_svc` (special-category, organisation identifiers, vendor checks), `billing_svc` (payment tokens, tax registration) hold KMS decrypt permission for their key; every decrypt of Sensitive business data writes `audit_event(view_sensitive)` before returning data (AT-46).
* **Rotation:** new writes use the new `key_version`; background re-encryption batches rows with older versions (query by `key_version`); old KEK versions are disabled after re-encryption completes.

### 5.2 Blind indexes (equality search on encrypted values)
* `HMAC-SHA256(k_purpose_vN, normalise(value))` stored as 32 bytes (CHECK `octet_length = 32`, BR-ORG-13) in `value_lookup_hash`, `tax_number_hmac`, `id_number_hmac`, `roll_number_hmac`, `contact_match_key.match_hash`; normalisation (case, whitespace, separators, checksum validation per `tax_id_type`) happens before hashing so equal numbers hash equally.
* Separate keys per purpose and per country/institution scope prevent cross-table correlation; the key lives in KMS, never in SQL (the ETL view example in the Grants sheet applies the HMAC in the loader).
* HMAC (not a plain hash) is required because tax numbers have low entropy and could otherwise be brute-forced from a leaked backup. Rotation: during a rotation window both versions are computed and either may match; a `key_version` column exists on the encrypted tables to drive the migration.

### 5.3 Tokenisation (vendor tokens)
Identity, payment and background-check vendors return opaque tokens/references stored as Sensitive strings (`candidate_identity_verification.vendor_token`, `payment_method_token.token_ref`, `background_check_order.vendor_order_ref`, `e_sign_request.vendor_envelope_ref`). Tokens are useless outside our vendor account, are never logged, never shown in the UI, and are purged on the vendor-specific schedule (e.g. `organisation_verification.vendor_token` after 90 days).

### 5.4 Masking rules
Rules live in views (no column grants): e-mail `a***@domain`, phone `+91*****1234`, person name first letter + `***`, birth date -> year, free text -> NULL, IP -> network prefix or NULL, salary -> NULL unless `salary_disclosure = disclosed`, coordinates -> 2 decimals. The sheet `MaskedViews` of the RBAC workbook proposes one view per table with Personal or Sensitive columns (198 tables) listing included, masked and excluded columns.

### 5.5 Never stored
Raw national identity numbers, card numbers (PAN), CVV, bank account numbers, UPI VPAs, plain passwords, plain tokens/API keys (plaintext shown once to the client), raw device fingerprints. Guard: schema review plus a column-name lint (BR-SUB-16) and test AT-34.

## 6. Password hashing

* **Algorithm:** argon2id, one-way, per-password random salt (PHC string `$argon2id$v=19$m=...,t=...,p=...$salt$hash` in `user_credential.password_hash`). **Default parameters** m = 64 MiB (65536 KiB), t = 3 iterations, p = 4 lanes, 32-byte output, 16-byte salt; OWASP 2024 minimum is m = 19 MiB, t = 2, p = 1 (stated in the column's pii text). The service benchmark targets 150-300 ms per hash on the auth pool hardware; parameters are raised, never lowered, when hardware allows.
* **Parameters stored per row** (`argon2_memory_kib`, `argon2_iterations`, `argon2_parallelism`, `hash_algorithm_id`, `pepper_version`) so a query finds hashes needing an upgrade: `SELECT app_user_id FROM user_credential WHERE is_active AND (argon2_memory_kib < 65536 OR argon2_iterations < 3 OR argon2_parallelism < 4 OR pepper_version < <current>)`; rehash happens transparently at the next successful login (`credential_change_reason` = rehash).
* **Pepper:** an HMAC-SHA256 pre-hash of the password with a secret from KMS (`pepper_version`); the pepper never enters the database; losing the DB alone does not allow offline cracking. Rotation: bump `pepper_version`, verify with both versions, rehash on login.
* **Policy:** minimum length 12, no composition rules, check against breached-password lists (k-anonymity range query; `breach_checked_at`, `breach_detected_at`, `must_change`), `expires_at` only for service-class or breach cases, one active credential per user (BR-ADM-03), history in the append-only `user_credential_history`.
* **Abuse control:** constant-time comparison, uniform error responses, throttling per identifier and IP, `login_attempt` evidence (BR-LIC-12), lockout with backoff, `security_event` for credential stuffing and MFA fatigue.
* **Where hashes can be read:** only `auth_svc` (GR-16); never in views, audit JSON, logs or exports (AT-12, AT-34).

## 7. Multi-factor authentication

* **Factors** (`mfa_factor`): TOTP (secret AES-256-GCM encrypted, `encryption_key_ref`), WebAuthn/passkeys (public key + counter, no secret), SMS/e-mail OTP only as a fallback with throttling; **recovery codes** (`mfa_recovery_code.code_hash`) single-use hashes, regenerated with audit (`mfa_change`).
* **Mandatory for:** super_admin, admin, account_admin (hardware key for staff), any sensitive permission step-up (decrypt of tax numbers, payout changes, role grants), and optional for other users with nudges. `identity_session.mfa_satisfied` records the state; step-up creates a new session id.
* **Defences:** push-fatigue detection (`security_event(mfa_fatigue)`), rate limits, enrolment of a new factor requires an existing factor or verified recovery channel plus notification on all channels, `device_trust_challenge` for new devices (code stored hashed, 30-day TTL).

## 8. Session controls (Rule group 9; B78)

* **Token model:** short-lived access token (about 15 minutes) + rotating refresh token. Refresh tokens are 256-bit random values; only `refresh_token_hash` (SHA-256) is stored in `identity_session`; each use inserts a child row (`parent_identity_session_id`) and marks the parent revoked (reason `rotated`); reuse of a revoked token revokes the whole family (`token_family_ref`) and raises `security_event(refresh_token_reuse)` (BR-ADM-16).
* **Timeouts:** idle timeout and absolute lifetime come from the licence (`session_idle_timeout_minutes`, `session_max_lifetime_hours`) and are stored per session (`expires_at`, `absolute_expires_at`, `last_used_at`); the login transaction releases stale sessions (BR-LIC-06 step 3) and a 1-minute job ends expired ones (BR-LIC-08).
* **Device binding and limits:** each session claims a `device_slot` (BR-LIC-05), device identity is an HMAC fingerprint; a refresh from a different fingerprint is refused or challenged; exceeding the licence limit is denied and recorded (`device_limit_violation`, `audit_event(device_limit_exceeded)`, `login_attempt(device_limit_denied)`, BR-LIC-07).
* **Revocation is auditable:** revoke device/session writes `device_revocation` / `session_revocation` and `audit_event` in one transaction (BR-LIC-09); revoked sessions do not count against the limit.
* **Fixation and theft:** a new session id is issued at login, at MFA step-up and at privilege change; cookies are `HttpOnly; Secure; SameSite=Lax/Strict` with CSRF tokens; tokens are never placed in URLs; `acting_organisation_id` binds the tenant context to the session, not to a request parameter.
* **Retention:** `identity_session` rows are purged by TTL 7 days after `expires_at`; `device_session` 13 months after `ended_at`; ended sessions keep audit value, active ones never expire silently (NULL `ended_at` is never TTL'd).
* **Tests:** AT-13, AT-14, AT-15, AT-48, AT-49.

## 9. Authorisation model and DB role model

* **Actors** (docket section 3): super_admin, admin, account_admin, guest, candidate, employer, recruiter, consultant, placement_officer, plus service roles. The full matrix (one row per table, CRUD codes, enforcement code G/V/A/T/N) is `docs/13_rbac_matrix.xlsx`; the rule set that generated it is sheet `Rules`.
* **DB roles:** about 20 group roles, never one per user (10M users would break pooling and bloat privilege data): persona pools (`app_guest`, `app_candidate`, `app_employer`, `app_recruiter`, `app_consultant`, `app_tpo`, `app_account_admin`, `app_staff_admin`, `app_staff_super`) and service tiers (`app_service`, `auth_svc`, `billing_svc`, `audit_writer`, `purge_svc`, `compliance_svc`, `etl_service`, `analytics_reader`, `audit_reader`, `backup_operator`, `migration_owner`). Objects are owned by `schema_owner` (NOLOGIN), granted to the migration login only during change windows, because owner and `admin` bypass REVOKE.
* **Where each docket rule is enforced:** recruiter only own company -> `vw_recruiter_job_requirement` + mapping chain (BR-ORG-01..03); consultant only open requirements -> `vw_consultant_open_requirement` + composite FK (BR-SRC-01/02); blocked party invisible -> `vw_candidate_visible_to_user` (BR-ADM-12..14); recruiters cannot register candidates -> `registration_policy` composite FK (BR-ADM-01); every sensitive action audited -> `permission.is_sensitive` + same-transaction audit (BR-ADM-11). See sheet `Enforcement` (E-01..E-38).
* **Viewer context:** viewer-scoped views (`vw_recruiter_job_requirement`, `vw_candidate_visible_to_user`) expose `viewer_app_user_id` and are read through `fn_recruiter_job_requirement(viewer)` / `fn_candidate_visible_to_user(viewer)` or a prepared statement with `viewer_app_user_id = $1`, injected by one data-access wrapper from the authenticated session. Custom session variables (`SET LOCAL app.viewer_id`) are **unverified** on the pinned image and are not relied upon (AT-25). The pair view `vw_candidate_visible_to_user` is a cross join and must never be queried without the viewer predicate (finding F-14; statement timeouts per pool role).
* **Append-only enforcement:** the 125 append-only tables get INSERT/SELECT grants only (GR-14); the matrix validation proves no actor has UPDATE or DELETE on them.
* **Resource guards:** `ALTER ROLE <pool> SET statement_timeout = ...` per pool (GR-29).
* **Extension, sub-roles inside an employer organisation** (out of scope per docket section 3): add `app_role` rows (organisation-scoped), `app_role_permission` rows with `data_scope` organisation or assigned_requirement, `app_role_eligibility` rows, optionally `job_requirement_member`; extend `vw_recruiter_job_requirement` with an EXISTS on the member role. No new DB roles are needed because the sub-roles are application-level permissions.

## 10. Audit design (B81)

* **What is audited:** every permission with `is_sensitive = true` and every action in sheet `AuditCoverage` of the RBAC workbook (credential and MFA changes, role and permission changes, consent, blocks, impersonation, break-glass, approvals, unmask/decrypt of PII, downloads/exports, wallet adjustments, erasure/purge, merges, configuration, device-limit violations, device/session revocation). High-volume facts (login attempts, views, deliveries, ledger rows) are recorded in their own append-only tables, not duplicated in `audit_event`. The action vocabulary (`audit_action`, 33 codes) lacks 0 codes and 0 entity types needed by stated rules (list in sheet `AuditRecommend`; test AT-43).
* **Record:** `audit_event` = actor (`actor_app_user_id`, `actor_type_id`, `impersonator_app_user_id`), `audit_action_id`, `audit_entity_type_id`, `entity_ref`, `organisation_ref`, `audit_outcome_id` (success/denied/failed), changed field names (before/after hold only changed fields; Personal values masked or HMAC tokens; credentials never), `reason_text`, `request_ref` (correlation), `identity_session_ref`, IP and user agent (Personal).
* **Atomicity:** the audit row is inserted in the same transaction as the action by a role that holds `audit_writer` (finding F-02), so there is no action without evidence (AT-44). Cross-service actions use an outbox.
* **Tamper evidence (P5):** 32 parallel hash chains; the writer locks `audit_chain_head(chain_no)` FOR UPDATE, assigns `chain_seq`, copies `prev_hash`, computes `row_hash = SHA-256(canonical fields || prev_hash)` and updates the head in the same transaction (BR-ADM-09). 32 chains bound write contention (one global chain would serialise all writes). `audit_chain_checkpoint` anchors signed segment heads in an object-lock bucket. A verifier job recomputes chains and raises `security_event(audit_chain_break)`.
* **Immutability:** INSERT/SELECT only for application roles (BR-ADM-08); a CockroachDB changefeed (`CREATE CHANGEFEED FOR TABLE audit_event INTO 's3://...'`) streams rows to an immutable bucket; hot rows are removed by row-level TTL (400 days) only after `sink_confirmed_at` and not while a legal hold exists (BR-ADM-10). Wallet ledger and ledger-like tables use the same pattern per wallet (BR-SUB-10).
* **Time index:** hash-sharded (bucket_count 16) so inserts do not hot-spot one range (D-02).
* **Reading:** `audit_reader` uses `vw_audit_event_redacted` (no IP/user agent, no before/after bodies); full rows only through `audit_export` with approval; the export is audited.
* **Operational audit outside the schema:** CockroachDB SQL audit/auth logs and KMS logs go to a SIEM with their own retention; backup runs are recorded in `docs/20_backup_restore_log.xlsx`.
* **Known gap:** IP/user-agent minimisation inside append-only tables (finding F-03).

## 11. Key management and rotation

| key / secret | purpose | custody | rotation | where recorded |
|---|---|---|---|---|
| TLS CA key | issues node/client certificates | offline, split custody | 10 years / on compromise | n/a |
| Node and client certificates | pgcrypto-free TLS and cert auth | cluster dir / service secret mounts | node 1 year, client 90 days | alerts 30 days before expiry |
| KMS KEK per purpose (mfa, compliance, tenant identifiers, messages, payment tokens) | wrap DEKs | KMS (HSM-backed), IAM per service identity | annual auto-rotation; versions retained until re-encryption done | `encryption_key_ref`, `key_version` columns |
| DEKs | encrypt fields | wrapped, cached in memory | on KEK rotation (lazy re-wrap) or per-tenant on request | envelope header / `key_version` |
| Password pepper | HMAC pre-hash for argon2id | KMS secret | yearly or on suspicion | `user_credential.pepper_version` |
| HMAC blind-index keys (identifiers, fingerprints, recipients) | equality search without disclosure | KMS secret, separate per purpose | every 2 years with dual-hash window | key_version where present |
| Backup key | backup encryption | separate KMS key, only `backup_operator` | yearly | backup log |
| Webhook / API secrets | provider signatures | secrets vault | per provider policy, at least yearly | `notification_provider.webhook_secret_ref`, vault |
| Audit checkpoint signing key | sign `audit_chain_checkpoint` | KMS asymmetric key | yearly; old public keys kept | checkpoint metadata |

Procedures: rotation = create new version, deploy to writers, dual-read, re-encrypt in batches, disable old, record in change log. **Compromise:** revoke IAM, rotate, re-encrypt affected columns first (Sensitive), force credential reset when the pepper or hash store is exposed, invalidate sessions, notify per incident process. No key appears in the repository, images, CI logs or SQL text.

## 13. Backup and restore security

Backups are as sensitive as the database. Plan, SQL and the timing log are in `docs/20_backup_restore_log.xlsx` (RTO 60 min / RPO 15 min for the 1M-profile laptop dataset; production target RTO 30 min / RPO 5 min). Security requirements: (1) encrypted with a key distinct from the data keys (KMS or passphrase from the vault); (2) written to a separate bucket/account with object lock and access logging; (3) `backup_operator` holds the database BACKUP privilege, no table SELECT; (4) restores only into the separate backup cluster, with new certificates, never to laptops or shared environments; (5) retention 35 days of PITR plus monthly fulls, with the erasure re-apply rule above; (6) restore parity test AT-45 (roles, grants, row counts, hash-chain verification); (7) licence note: RESTORE needs no Enterprise licence, BACKUP and encrypted backups are **unverified** (check on the image).

## 14. Secrets handling and logging hygiene

* **Secrets:** a secrets vault/KMS holds every secret; the database stores only references (`credential_vault_ref`, `webhook_secret_ref`), hashes, ciphertext. Repository: no secrets; `.env.example` files contain placeholders; local development files (for example `infra/*/local.env`) must contain throw-away values only (they serve insecure laptop clusters where passwords are ignored); real secrets live only in gitignored `.env` files. CI uses short-lived federated credentials; images are pinned by digest.
* **Logging:** application logs use structured fields with an allow-list (ids, codes, outcomes); e-mail, phone, tokens, tax numbers, request bodies and SQL parameters are never logged; error responses carry no SQL text. CockroachDB logs: enable redactable logs and keep statement/audit logs for security-relevant tables only; diagnostics bundles are produced with redaction (`EXPLAIN ANALYZE (REDACT)`; `cockroach debug zip --redact`; verify exact flags on the image).
* **Test:** AT-35 greps all logs of the test run for emails, phones, JWTs and tokens (0 hits).
