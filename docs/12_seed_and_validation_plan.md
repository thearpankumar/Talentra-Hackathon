## 1. Principles and reproducibility

* The generator is part of the deliverable (docket Section 6): it reads the data dictionary, never a hand-copied schema, so a model change is picked up on the next run.
* All randomness comes from one master seed (`20261015`); each table and shard derives its own stream (`sub_seed = int(sha256(f'{master}:{table}:{shard}')[:8], 16)`), so tables can be generated in parallel and re-generated alone with identical output.
* Primary keys are generated client-side as UUIDv4 values drawn from the table's seeded stream (the DB default `gen_random_uuid()` is not used during seeding): FK values are known before insert, runs are bit-reproducible, and idempotent re-load is possible (`INSERT ... ON CONFLICT (id) DO NOTHING`).
* Seeded rows pass through the normal constraints (CHECK, UNIQUE, FK): the seed is the first test of the schema. Rows that must be *rejected* are produced separately as negative tests (section 5.3), never loaded as data.
* The seeding role is `migration_owner` (data DML window), not the application roles; append-only tables are loaded in INSERT-only fashion.

## 2. Load order (topological sort of the FK graph)

Computed from the 2951 foreign keys of the dictionary (`ForeignKeys` sheet equivalent). Algorithm: build the child->parent graph over tables; self-referencing FKs (39) are excluded from the graph and handled inside the table (roots first, then children ordered by depth); strongly connected components are broken at nullable FK edges (MATCH SIMPLE: a NULL in any FK column skips the check) and the removed edge becomes a deferred UPDATE; the remaining DAG is layered by longest path: **wave(t) = 0 if no parent, else 1 + max(wave(parent))**. Tables in the same wave have no FK between them and are loaded in parallel. Result: **20 waves**, 1306 tables.

## 3. Row-count targets and the long-tail rule

Total seeded rows at laptop scale: **295,885,709** in 1306 tables (full-scale projection 4,299,284,309). Estimated load time at an assumed 60,000 rows/s aggregate (`COPY` over 4 parallel streams; throughput is unverified until the first load): **1.4 h**.

* **Docket-fixed anchors**: `candidate_profile` 1,000,000; `job_requirement` 100,000; `job_application` 5,000,000 (never trimmed).
* **Explicit anchors** (211 tables) in `perf_model.ANCHORS`: children of the fixed entities (e.g. `candidate_skill` 8,000,000, `job_application_status_history` 15,000,000), identity/audit volumes, wallet/payments, notification streams, gig, analytics facts. TTL'd event streams are seeded as a window sample of the steady state (`TRIM` dictionary) so the laptop stores about 173 GiB logical (doc 11 section 1).
* **Long-tail rule** (the remaining 557 non-lookup tables): rows by dictionary volume class: low 1,000, medium 20,000, high 150,000, very_high 500,000; analytics tail 1,000 / 20,000 / 100,000 / 500,000; `tier3_reference` low 500 / medium 20,000; **extension modules (ext_*) at 5%** of the class value (minimum 100 rows) because they are sparse labelled extensions; parents drive children: a tail child never exceeds `parent_rows x avg_children` (generator caps it).
* **Lookups** (538 tables): all codes and languages of the Enums sheet; no random rows.
* **Full scale** = laptop x driver factor (profiles 10, jobs 10, applications 20, other 10, fixed reference 1); never loaded (docket), extrapolated in doc 11.
* **Fallback if disk exceeds 330 GiB cluster-wide** (3 x the measured per-replica size): halve the non-docket event streams (`job_view_event`, `candidate_activity_log`, notification family, `fact_*`, `login_attempt`) via `--scale-events 0.5`; docket-fixed tables unchanged.

## 5. Duplicates, multilingual names, overlap attempts, data-quality issues

### 5.1 Candidate duplicates and multilingual names

* **Duplicate rate: 3% of profiles (30,000 profiles are duplicates of another person)**, created by cloning a base profile with one or more perturbations: transliteration variants (Hindi/English), swapped given/family name, nickname, typo (edit distance 1-2), different email with the same phone, same email on a legacy copy, differently formatted phone. The pair goes into `duplicate_candidate_match` (45,000 rows: multiple rules can fire per pair; `match_confidence` 0.55-0.99; 60% reviewed by a seeded admin).
* **Identity-token duplicates**: 0.3% reuse the same `id_number_hmac` (must be rejected by the active-binding unique index when both claim it: N-21).
* **Name mix (Rule 7, UTF-8 end to end)**: Latin 60% (incl. diacritics), Devanagari 14%, Tamil 4%, Telugu 4%, Bengali 4%, Arabic 4%, CJK 4%, Cyrillic 3%, other 3%. Name lengths 2-150 characters, 0.1% at the 150 limit. `profile_language_id` consistent with the script (95%); 5% deliberate mismatch. Each language keeps a matching UI label set for the translation test.
* Generated with locale-specific name lists (Faker locales `en_IN`, `hi_IN`, `ta_IN`, `te_IN`, `bn_BD`, `ar_AE`, `zh_CN`, `ru_RU`, `de_DE`, `fr_FR`) plus NFC/NFD variants (0.2% store NFD to test normalisation).

### 5.3 Data-quality issues injected

Constraints reject dirty values in the typed tables, so most issues are injected into the **legacy import path** (`profile_import.raw_payload`, staging files) and must be cleaned or rejected by the loader; each has a detector in section 6.

| issue | rate | where | detection / expected handling |
|---|---|---|---|

## 9. Idempotency, reproducibility, execution

| aspect | design |
|---|---|
| Re-run safety | every INSERT is `ON CONFLICT DO NOTHING` on the primary key (deterministic ids) and on the table's natural/idempotency key; a second run of the same seed changes 0 rows; a changed seed or scale uses `--clean` (drop database and restore the empty-schema backup) rather than partial deletes. |
| Manifest | `seed_manifest.json`: master seed, generator version, dictionary SHA-256, per-table row count and SHA-256 of the ordered id list; two runs must produce identical manifests (reproducibility test). |
| Order | wave order of section 2; inside a wave tables load in parallel (4 workers); inside a table, shards of 100,000 rows with their own sub-seed; transactions of 5,000-20,000 rows (`COPY` for tables without FKs to uncommitted data; batched `INSERT` otherwise); retry on SQLSTATE 40001. |
| Throughput protections | `SET CLUSTER SETTING kv.bulk_io_write.max_rate` unchanged; index creation after load is NOT used (indexes exist during load so the measured write cost is realistic); optional `SET CLUSTER SETTING sql.stats.automatic_collection.enabled = true` and a final `CREATE STATISTICS` on the 20 key tables before B70. |
| Seed checkpoints | after waves 0-2, after profile, after jobs/applications, after money: `BACKUP INTO` a local external connection so the B80 restore test and re-runs can start from a checkpoint (backup storage for Docker: see crdb_capabilities.md section 2.5). |
| Time | expected 1.4 h for 295,885,709 rows at the assumed throughput; docket B60/B61 subsets (profiles, jobs, applications) are about 36 min of that. |


## 10. Hand-off to the ingestion engine

`ingestion-engine/` (separate component, not modified here) introspects the live database through `information_schema` and, when `DATA_DICTIONARY_PATH` points at `docs/05_data_dictionary.xlsx`, enriches columns with classification and description (`load_data_dictionary` accepts any sheet whose headers contain `table`, `column` and `classification`/`sensitivity` or `description`). The dictionary contract the engine and any DDL/seed generator may rely on is `docs/05_data_dictionary_schema.md`; the stable sheets and headers are:

| sheet | headers (stable; new columns only appended) | used for seeding |
|---|---|---|
| Tables | table, module, owner, kind, delete_policy, volume, tier, milestones, max_sensitivity, column_count, audit_columns, ttl, partitioning, retention, description | volume -> row target class; kind -> generator; delete_policy -> append-only loading; ttl -> window sizing |
| Columns | table, ordinal, column, type, domain, nullable, nullability_justification, default, sensitivity_class, delete_policy, pii_treatment, computed_expr, is_pk, fk_ref, standard_column, description | type/domain -> value generator (money, email, phone, latitude, ...); nullable -> NULL rate with null_why; sensitivity_class -> synthetic-only masking rules; fk_ref -> parent lookup; computed_expr -> skip column |
| Enums | lookup_table, code, sort_order, is_active, language_tag, display_name, description | seeds the 536 lookup tables (name_i18n built per code) |
| Indexes | table, index_name, columns, unique, hash_sharded, bucket_count, inverted, where_predicate, storing, kind, description | unique/partial-unique indexes = uniqueness rules the generator must respect (e.g. one open block per pair) |
| Constraints | table, constraint_name, constraint_type, columns, expression, description | UNIQUE and CHECK expressions parsed into generator constraints (ranges, enumerations) |
| ForeignKeys | table, fk_name, columns, ref_table, ref_columns, on_delete, on_update, ref_module, cross_module, index_exempt, description | topological load order (section 2), composite FK (organisation_id, id) pairs, deferred nullable edges |
| Views, Partitioning | view_name ...; table, module, volume, strategy, key_or_columns, naming_pattern, notes | views for validation queries; partitioning notes for zone configs |


Recommended engine behaviour for this dataset: (1) read `Tables`/`ForeignKeys` and compute the same waves as `gen_seed_plan.py` (the script's `load_order()` is the reference implementation: SCC break at nullable FK edges, longest-path layering); (2) treat `volume` and the `perf_model.ANCHORS` table as the row-target source, not free choice; (3) generate PKs client-side; (4) respect partial unique indexes from the `Indexes` sheet by sampling without replacement; (5) emit the negative-test stream of section 5.2 from the `NEG` list (JSON export: `python docs/tools/gen_seed_plan.py --json`); (6) run the validation suite after load and write the manifest. Mapping to the engine's own model: `Table.fks` <- ForeignKeys, `Column.classification` <- Columns.sensitivity_class, `Column.enum_values` <- Enums.
