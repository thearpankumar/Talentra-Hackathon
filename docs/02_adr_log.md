## ADR-001: Engine: CockroachDB v26.2 (PostgreSQL dialect) instead of PostgreSQL or MySQL

**Status:** Accepted  |  **Date:** 2026-10-16  |  **Milestones:** B1, B2

**Context.** Docket Section 1 and backlog B1 ask the team to fix a provider (PostgreSQL or MySQL) and justify it. The platform has a stated target of 10M candidate profiles, 1M job requirements and 100M applications, concurrent logins that must respect device limits, an append-only money ledger and 24x7 notification/audit write streams.

**Decision.** Use CockroachDB, PostgreSQL dialect/wire protocol, assumed target v26.2 (Regular GA 26.2.0-26.2.6; LTS from v26.2.7, maintenance to 2027-09-23). The image tag must be pinned to the latest 26.2.x patch after checking Docker Hub (exact tag unverified in crdb_capabilities.md). DDL stays in the PG dialect; CockroachDB-specific constructs are limited to: hash-sharded indexes, row-level TTL, STORING indexes, STRING/INT2/INT4/INT8 type spellings and `CREATE INDEX ... USING GIN`.

**Alternatives considered.** (A) PostgreSQL 16/17 single primary with declarative partitioning (and Citus/read replicas for scale); (B) MySQL 8 InnoDB; (C) CockroachDB v26.3 (Innovation release, shorter support, no Assistance Support).

**Reason.** SERIALIZABLE is the default isolation, which makes the rules without exclusion constraints (device limit, non-overlap, wallet) provable by unique indexes plus transactions; random UUID keys and hash-sharded indexes remove single-range write hotspots; online schema changes and multi-node survival match the 24x7 audit/notification workload; PG wire compatibility keeps drivers, ORMs and DDL review familiar. MySQL was rejected because it has no partial indexes (needed for soft-delete uniques, one-open-row rules and device slots), and PostgreSQL because write scale beyond one primary needs sharding middleware.

**Trade-off.** LICENCE CAVEAT (crdb_capabilities.md section 3): binaries from 24.3 are under the CockroachDB Software License; every multi-node self-hosted cluster needs a licence key (Enterprise Free only if company+affiliates revenue < US$10M, own hardware or own public-cloud account, annual renewal, telemetry required; 30-day Trial otherwise). Without a valid key a cluster is throttled to 5 concurrent open SQL transactions (after 7 days). `cockroach start-single-node` and `cockroach demo` need no licence. Missing features we design around: exclusion constraints, MERGE (no docs page), CREATE DOMAIN (GA only in v26.3), column-level privileges, session advisory locks, uuid_v7 (not found in docs); DEFERRABLE FKs and NOT VALID are unverified. The docket names PostgreSQL or MySQL; CockroachDB is treated as the PostgreSQL family and this is recorded as a deviation (DEV-01 in 08_rule_compliance.xlsx).

**Consequences.** Apply the licence key right after `cockroach init`, ensure telemetry egress, prefer Enterprise Free over Trial. Patterns P1-P6 replace missing features (19 CHAIN_FK, 6 SLOT_TABLE, 89 PARTIAL_UNIQUE, 33 TXN_LOCK business rules). Portability list to stock PostgreSQL: drop `USING HASH` (use plain btree), replace TTL by a cron DELETE, rename STRING->text/varchar, remove STORING (INCLUDE). Several CHECKs use `~` and jsonb `?` (crdb_capabilities row 5: must be smoke-tested on the target image).

**Related tables:** app_user, licence, device_slot, gig_slot, subscription_period

**Related business rules:** BR-LIC-06, BR-SUB-03, BR-GIG-01

## ADR-002: Primary keys: random UUIDv4 (gen_random_uuid) rather than bigint, UUIDv7 or hash-sharded PKs

**Status:** Accepted  |  **Date:** 2026-10-16  |  **Milestones:** B20, B22, B33

**Context.** Rule group 2 requires a stated, consistently applied surrogate key type. Sequential keys (SERIAL/sequences, time-ordered UUIDs) create a hot range in a distributed key-value store.

**Decision.** Every one of the 1306 tables has `id UUID NOT NULL DEFAULT gen_random_uuid()` as PK (injected by dictlib.inject_standard); every FK column is UUID. No SERIAL, no sequences. Natural keys (email, GSTIN hash, external ref, lookup code) are UNIQUE constraints/indexes, never PKs. Only analytics dim_date and dim_time_of_day use deterministic UUIDv5 ids (documented exception, see ADR-021).

**Alternatives considered.** (A) INT8 `unique_rowid()` (docs: acceptable, not strictly ordered, 48-bit time prefix); (B) sequences with CACHE; (C) UUIDv7/ULID (time-ordered); (D) `PRIMARY KEY (id) USING HASH` on a bigint.

**Reason.** Docs strongly recommend UUIDv4 and `gen_random_uuid()` spreads inserts over all ranges, so a table never becomes a single-range write hotspot at 100M rows. UUIDv7 is not available (`uuid_v7()` not found in the v26.2 docs) and docs warn other UUID layouts 'require performance testing to avoid hotspots'. Sequences are replicated writes and leave gaps on rollback. UUIDs are non-guessable in URLs (no tenant-id enumeration).

**Trade-off.** 16-byte keys inflate every secondary index and FK column versus 8-byte ints (index size and RAM cache hit ratio cost, measured in B70-B74). Keys carry no creation order, so every time-ordered read needs a real timestamp column and index. `gen_random_uuid()` skips uniqueness checks by default (`sql.optimizer.uniqueness_checks_for_gen_random_uuid.enabled` is off): relevant only if implicit partitioning (REGIONAL BY ROW) is adopted, see ADR-018.

**Consequences.** Gapless human-facing numbers (invoice number) cannot come from keys: invoice_number_series is a locked counter row (BR-SUB-12). Support-ticket numbers are random base32. Time-range scans always use hash-sharded timestamp indexes (ADR-003).

**Related tables:** app_user, candidate_profile, job_application, wallet_ledger_entry, invoice_number_series, dim_date

**Related business rules:** BR-SUB-12

## ADR-003: Hash-sharded secondary indexes for time-ordered columns on high-volume tables

**Status:** Accepted  |  **Date:** 2026-10-16  |  **Milestones:** B57, B70, B73, B74

**Context.** 299 tables are marked high/very_high volume. Indexes on created_at, applied_at, occurred_at, expires_at or status+time receive monotonically increasing keys and would all land in the last range.

**Decision.** Time-ordered indexes use `USING HASH WITH (bucket_count = n)`: 189 hash-sharded indexes on 173 tables (bucket_count 8: 34, 16: 117, 32: 38). Per-entity access paths lead with the random entity id and are plain btrees. High/very_high tables without a hash index (135) must justify it in `no_hash_why` (162 tables do) because their only access paths are random-id-led.

**Alternatives considered.** (A) plain btree on timestamp (hotspot); (B) PK `USING HASH` (keys are already random); (C) explicit PARTITION BY RANGE(month) (no physical partitions chosen, ADR-017); (D) application-computed shard column.

**Reason.** Documented CockroachDB mechanism; shard column is VIRTUAL (no backfill since v22.1); lint-enforced (warning when a high/very_high table has neither a hash index nor `no_hash_why`).

**Trade-off.** Range scans over a hashed index fan out to every bucket (small performance hit per docs); more buckets than nodes gives diminishing returns (job_application uses 32 for an assumed 8-node cluster: tune at deployment); a hash-sharded index cannot carry explicit PARTITION BY key columns. Hash + partial combinations (e.g. idx_device_session_expires_at WHERE ended_at IS NULL) are flagged in notes to be tested at seed time.

**Consequences.** Reports needing a time range must keep the range narrow or read a rollup (agg_* tables, analytics). Retention TTL jobs scan the same hashed index.

**Related tables:** job_application, notification_delivery, audit_event, login_attempt, device_session, gig_slot

## ADR-004: Delete policy per table: soft, hard or append_only

**Status:** Accepted  |  **Date:** 2026-10-16  |  **Milestones:** B20, B22, B33, B59

**Context.** Rule group 4 requires every entity to be classified soft- or hard-deleted, audit records append-only, and retention stated per entity.

**Decision.** Each table carries `delete_policy`: soft = 260 tables (deleted_at/deleted_by injected, natural uniques become partial `WHERE deleted_at IS NULL`); hard = 921 (lookups, links, derived/cache rows, config, mutable snapshots); append_only = 125 (history, ledgers, audit, views/downloads, login attempts, facts: INSERT/SELECT grants only, corrections are new rows). Retention text is mandatory on every table; lookups are retired by is_active, never deleted.

**Alternatives considered.** (A) soft-delete everywhere; (B) hard delete + separate archive tables; (C) temporal tables/history-table per entity.

**Reason.** Soft only where users or regulation may restore data or where history rows reference the entity (candidate_profile, job_requirement, job_application, organisation, wallet); everything else avoids dead rows that slow indexes and TTL. Append-only maps directly to docket rule groups 4 and 10.

**Trade-off.** Soft tables need partial unique indexes and `deleted_at IS NULL` predicates everywhere (partial predicates cannot use now()); FKs cannot point at a partial unique index, so soft-deleted parents stay referenceable. 18 tables are `created_only` but not append_only (17 agg_* upserts and gig_slot): they intentionally lack updated_* (see 07, DEV-03).

**Consequences.** Physical deletion is performed only by erasure/retention jobs (purge_service role, data_retention_policy), by TTL, or by FK CASCADE from soft parents in bounded batches.

**Related tables:** candidate_profile, job_requirement, job_application, organisation, wallet, audit_event, wallet_ledger_entry, data_retention_policy, purge_job_run

## ADR-005: Gigs are a separate subsystem (gig_*), not a job_requirement variant (D-15)

**Status:** Accepted  |  **Date:** 2026-10-16  |  **Milestones:** B26, B29, B32, B35

**Context.** The docket lists the gig marketplace as the primary revenue category but with different semantics from permanent/staffing jobs: a window and a price, one-direction bids, external fulfilment, and a non-overlap rule per worker (B35).

**Decision.** A separate subsystem of 65 tables (34 non-lookup) prefixed gig_*, sharing only master data (job_category, skill, country, city, currency, language), organisation, app_user, wallet/payment and notifications. Reporting is unified by `vw_unified_demand` and analytics `dim_demand_type`/`vw_unified_demand_daily`.

**Alternatives considered.** (A) single job_requirement with a job_kind discriminator; (B) shared work_item supertype with gig/job subtype tables (CockroachDB has no table inheritance); (C) separate subsystem (chosen).

**Reason.** A shared table needs 10+ discriminator-dependent nullable columns and weak type-dependent CHECKs; the job pipeline (shortlist, interview, offer, join) is wrong for gigs (bid -> accept -> external fulfilment); gig-only integrity (price xor rate, rate only completed work, one list entry, slots) is expressible as declarative constraints on gig tables.

**Trade-off.** Cross-type demand reports need a UNION (mitigated by the view); skill/category matching logic exists twice (mitigated by shared master tables); a third work type (managed remote workforce) would be a third subsystem and another UNION branch.

**Consequences.** Candidate projects reuse one candidate_project table with an exactly-one owner CHECK (candidate or gig worker) so completed gigs become verified projects.

**Related tables:** gig_request, gig_application, gig_assignment, gig_worker_profile, job_requirement, job_application, candidate_project, vw_unified_demand, dim_demand_type

## ADR-006: Wallet ledger: append-only, hash-chained, corrections by reversal rows (D-14)

**Status:** Accepted  |  **Date:** 2026-10-16  |  **Milestones:** B41, B44, B47, B38

**Context.** Rule group 10: payment and wallet ledgers are append-only and a correction is a new entry that references the original. Credits are consumed concurrently (downloads, outreach, postings) so the balance must never go negative and a retried request must not double-charge.

**Decision.** wallet_ledger_entry is INSERT/SELECT-only for application roles. Columns: sequence_no (UNIQUE per wallet), idempotency_key (UNIQUE), reverses_wallet_ledger_entry_id (UNIQUE: a row can be reversed once), balance_after, prev_hash/row_hash chain. wallet holds credit_balance and ledger_sequence, updated in the same SERIALIZABLE transaction under `SELECT ... FOR UPDATE`; CHECK credit_balance >= 0 and ledger-entry balance_after >= 0 are the backstops. A composite self-FK (wallet_id, prev_sequence_no) -> (wallet_id, sequence_no) makes the sequence gap-free. A changefeed ships ledger rows to an immutable sink and a nightly job verifies chains and `vw_wallet_balance_drift`.

**Alternatives considered.** (A) mutable balance + audit log; (B) event sourcing with balance computed on read; (C) ledger without chain; (D) double-entry journal (ADR-007).

**Reason.** Append-only plus unique keys give an auditable, idempotent money trail; lock + CHECK + UNIQUE together mean correctness does not rest on the best-effort FOR UPDATE lock (docs: under SERIALIZABLE the lock may be lost on lease transfer and the txn then retries with 40001).

**Trade-off.** The wallet row is a deliberately hot row (one writer per wallet); throughput per wallet is bounded by transaction latency. The hash chain is per wallet (verification cost grows with entries). Optional `enable_durable_locking_for_serializable` for the billing role.

**Consequences.** Download deductions point the other way (profile_download.wallet_ledger_entry_id UNIQUE) because there are no deferrable FKs; the row is created right after the ledger row in the same txn. Hash-chain tables in the model: ad_budget_ledger, audit_event, moderation_action_log, notification_delivery_daily_summary, wallet_ledger_entry.

**Related tables:** wallet, wallet_ledger_entry, profile_download, vw_wallet_balance_drift, refund, payment_order

**Related business rules:** BR-SUB-08

## ADR-007: Wallet unit is integer credits, single-entry ledger; double-entry accounting left as an extension

**Status:** Accepted  |  **Date:** 2026-10-16  |  **Milestones:** B38, B44, B47

**Context.** Recruiter products (downloads, outreach messages, postings) are priced in credits that vary by plan and expire in lots; money appears only at purchase.

**Decision.** wallet.credit_balance and wallet_ledger_entry.credits_delta are INT8 credits; one wallet per owner (organisation XOR user, CHECK ck_wallet_one_owner) and currency; money lives in payment_order/invoice as DECIMAL(18,4) + currency_id (D-06). Lots (wallet_expiry_bucket, wallet_bucket_consumption) give FIFO expiry. A ledger_account + journal_line pair for full double-entry accounting is an extension point; finance receives a nightly export.

**Alternatives considered.** (A) money wallet with FX; (B) full double-entry in the OLTP schema; (C) credits only (chosen).

**Reason.** Integer credits make balance CHECKs and hash chains exact (no rounding), and avoid converting balances across currencies (a pack bought in INR is refunded in INR).

**Trade-off.** Revenue recognition (deferred revenue, breakage) is not queryable from the OLTP ledger alone; it needs the export or the proposed journal tables.

**Consequences.** Status Proposed for the double-entry extension only; the single-entry design is Accepted. Gig escrow and payouts reuse wallet/payment_order (D-15).

**Related tables:** wallet, wallet_expiry_bucket, wallet_bucket_consumption, payment_order, invoice, credit_rate_card

**Related business rules:** BR-SUB-08

## ADR-008: Device limit enforcement: pre-created slots plus a seat row lock at login (D-13)

**Status:** Accepted  |  **Date:** 2026-10-16  |  **Milestones:** B36, B39, B42, B45

**Context.** Rule groups 2 and 9: a user must not hold more active sessions than the licence allows devices, the limit must be enforced at login under concurrency, the breach must be audited, and expired/revoked sessions must not count.

**Decision.** licence has max_users and max_devices_per_user (positive CHECKs). licence_seat_slot pre-creates slots 1..max_users per licence; device_slot pre-creates 1..max_devices_per_user per licence_seat. Each active device_session claims one device_slot: `uq_device_session_device_slot_id` partial unique WHERE ended_at IS NULL. Login runs in a SERIALIZABLE txn: `SELECT ... FROM licence JOIN licence_seat ... FOR UPDATE OF s` (locks only that user's seat), releases stale sessions, picks a free slot or applies device_limit_policy (deny_new or replace_oldest). A breach writes device_limit_violation + audit_event + login_attempt(device_limit_denied) in a txn that commits the evidence. A session counts iff ended_at IS NULL; revoke sets ended_at/end_reason and writes session_revocation/device_revocation + audit_event.

**Alternatives considered.** (A) COUNT(*) check in the application; (B) lock only (no declarative twin); (C) counter column on the licence_seat; (D) exclusion/trigger based approach (unavailable or not relied upon).

**Reason.** The slot unique index cannot be bypassed by an application bug, while the FOR UPDATE row lock gives ordered, low-retry execution and a clean place to record the violation; locks are per seat so different users never contend.

**Trade-off.** Slot rows must be maintained when the licence limit changes (BR-LIC-14: the limit-change txn marks surplus slots is_retired, never deleting a held one); lock durability under SERIALIZABLE is best-effort so 40001 retries (max 5, jittered) are part of the protocol.

**Consequences.** device_session is very_high volume (TTL 13 months on ended_at; NULL ended_at never expires). Fingerprints are HMAC hashes only. Login history is the view vw_login_history over login_attempt, so there is one write path.

**Related tables:** licence, licence_seat_slot, licence_seat, device_slot, device_session, device_limit_violation, login_attempt, audit_event, device_revocation, session_revocation, vw_login_history

**Related business rules:** BR-LIC-01, BR-LIC-02, BR-LIC-05, BR-LIC-07, BR-LIC-14, BR-LIC-06

## ADR-009: Non-overlap without exclusion constraints: chain FK (P1), slot table (P2), partial unique (P3)

**Status:** Accepted  |  **Date:** 2026-10-16  |  **Milestones:** B34, B35, B47

**Context.** Docket rules require non-overlapping subscription periods per licence (rule group 10, B47), non-overlapping gig windows per worker (B35) and effective-dated recruiter mapping (B34). CockroachDB has no exclusion constraints.

**Decision.** P1 CHAIN_FK for consecutive periods: sequence_no, prior id UNIQUE, copied prior end date, composite FK (prior_period_id, licence_id, prior_period_end_date) -> (id, licence_id, period_end_date) ON UPDATE RESTRICT, CHECK start >= prior end, partial unique root. Used by subscription_period and recruiter_organisation_mapping (19 CHAIN_FK rules in total). P2 SLOT_TABLE for windows: gig_assignment windows on a 15-minute grid are exploded into gig_slot rows UNIQUE(gig_worker_profile_id, slot_start_at) in the same txn (6 SLOT_TABLE rules). P3 partial unique `WHERE effective_to IS NULL` for one open row. P4 FOR UPDATE only adds friendly errors.

**Alternatives considered.** (A) range column + application check (race-prone); (B) btree_gist exclusion (not in CockroachDB); (C) triggers (not relied upon, ADR-012); (D) serialisable-only logic.

**Reason.** Each pattern is declarative: the proof for P1 is by induction (each period has <= 1 successor, starts at/after predecessor end, frozen by ON UPDATE RESTRICT); P2 collides on at least one slot for any overlap, so concurrency is handled by the unique index.

**Trade-off.** P1 forbids editing a non-tail period end; shortening is allowed only on the tail; lengthening/back-dating uses cancel-and-reissue. P2 costs rows: a 31-day max assignment = 2,976 slots, ~40 slots per typical gig, TTL keeps 90 days (gig_slot is very_high volume with a hash-sharded slot_start_at index).

**Consequences.** gig_slot has no updated_* columns (insert/delete only). vw_subscription_period_overlap must return 0 rows and is part of validation (B66/B79). mentor session overlap is only start-time unique (extension noted).

**Related tables:** subscription_period, recruiter_organisation_mapping, gig_slot, gig_assignment, vw_subscription_period_overlap

**Related business rules:** BR-SUB-03, BR-GIG-01, BR-ORG-01

## ADR-010: Organisation hierarchy cycles prevented by level-increment composite FK

**Status:** Accepted  |  **Date:** 2026-10-16  |  **Milestones:** B28, B34

**Context.** Organisation hierarchy (B28/B34) needs a tree without cycles; no triggers (ADR-012) and recursive-CTE checks race under concurrency.

**Decision.** organisation_hierarchy keeps one row per organisation with hierarchy_level (0..7), parent_level, root_organisation_id and ancestor_path; a self composite FK (parent_organisation_id, parent_level) -> (child_organisation_id, hierarchy_level) and CHECK hierarchy_level = parent_level + 1 make every edge go down one level exactly. organisation_hierarchy_closure (ancestor, descendant, depth) is derived in the same transaction and re-checked nightly.

**Alternatives considered.** (A) adjacency list + recursive CTE guard; (B) closure table only; (C) nested sets; (D) triggers.

**Reason.** A cycle would need a level to equal itself plus k, which is unrepresentable; the closure gives O(1) subtree reads for vw_recruiter_job_requirement.

**Trade-off.** Re-parenting a subtree changes descendants' levels: one multi-row UPDATE inside a SERIALIZABLE txn (FK checked at statement end); the 8-level cap bounds it.

**Consequences.** The same trick is reused for organisation_department.

**Related tables:** organisation_hierarchy, organisation_hierarchy_closure, organisation_department, organisation

## ADR-011: Multi-tenancy by organisation with composite-FK tenant pinning and view-based recruiter scoping (D-11)

**Status:** Accepted  |  **Date:** 2026-10-16  |  **Milestones:** B28, B34, B33, B79

**Context.** Docket Section 3: a recruiter may only see and act on job requirements assigned to their company; consultants only on requirements open to consultants; privileges must be enforced in the database or access layer.

**Decision.** Tenant = organisation. Tenant-scoped tables carry organisation_id and, where a child must provably belong to the same tenant, a composite FK to the parent's UNIQUE(organisation_id, id) (job_application -> job_requirement(organisation_id, id); candidate_shortlist_item -> candidate_shortlist_folder). Recruiter access = effective-dated recruiter_organisation_mapping read through the view vw_recruiter_job_requirement; application roles have no direct SELECT on job_requirement for recruiter personas. Consultants go through consultant_job_openness and vw_consultant_open_requirement. Authorisation data (app_role, permission, app_role_permission with data_scope) is in the administration module.

**Alternatives considered.** (A) schema-per-tenant; (B) database-per-tenant; (C) shared tables + row-level security policies as the only guard; (D) shared tables + tenant column checked by application only.

**Reason.** Shared tables scale to millions of tenants without DDL fan-out; composite FKs make cross-tenant child rows impossible even if the application has a bug; views give a stable, auditable access path.

**Trade-off.** Schema-per-tenant isolation and per-tenant backups are lost; row filtering relies on views + grants because CockroachDB has no column-level privileges and RLS is only optional hardening (ADR-012). A view `vw_recruiter_job_requirement` is defined in both jobs_applications and organisation_account (duplicate name; one must be dropped at integration, see 07 risk R-11).

**Consequences.** Every new tenant table needs `uq_<table>_id_organisation_id` for children to pin to. Cross-module mapping/organisation equality is partly view + application enforced (open question recorded in jobs notes).

**Related tables:** organisation, recruiter_organisation_mapping, job_requirement, job_application, candidate_shortlist_item, candidate_shortlist_folder, job_consultant_openness, app_role, permission, app_role_permission, app_user_role, vw_recruiter_job_requirement, vw_consultant_open_requirement

## ADR-013: Audit trail: append-only, 32 parallel hash chains, changefeed to an immutable sink

**Status:** Accepted  |  **Date:** 2026-10-16  |  **Milestones:** B33, B59, B78, B79, B81

**Context.** Rule group 4: audit records are append-only and application users cannot update/delete them; docket Section 3 requires every sensitive action to be recorded; B59/B78 ask for tamper evidence.

**Decision.** audit_event (very_high, append_only, created_only audit mode) is INSERT/SELECT-only for app_rw/audit_writer (`REVOKE UPDATE, DELETE`, BR-ADM-08). 32 parallel chains: the writer locks audit_chain_head(chain_no 0..31) FOR UPDATE, assigns chain_seq, copies prev_hash and computes row_hash = SHA-256(canonical fields || prev_hash); CHECK (chain_seq = 1) = (prev_hash IS NULL). audit_chain_checkpoint anchors signed segments in an object-lock bucket; a changefeed streams audit_event to that bucket; row-level TTL (400 days on occurred_at) runs only after the checkpoint sink_confirmed_at and when no legal_hold exists (BR-ADM-10, job pauses TTL otherwise).

**Alternatives considered.** (A) single global chain (serialises all writes); (B) no chain, grants only; (C) database audit log feature only (not in the data model); (D) per-table audit shadow tables.

**Reason.** 32 chains bound contention while keeping per-chain tamper evidence; checkpoints give an external anchor; a single audit table keeps queries uniform (actor, entity, request).

**Trade-off.** A verifier job is needed (security_event audit_chain_break); TTL deletes run as table owner so the app-role REVOKE does not block them; audit_event.entity_ref/organisation_ref/request_ref are deliberately FK-less (polymorphic or must survive the row).

**Consequences.** All modules write audit_event for sensitive actions (device_limit_violation holds audit_event_id FK). The time index idx_audit_event_occurred_at is hash-sharded (16 buckets). TTL-after-confirmation is a job rule, not a declarative one (limitation recorded in 07).

**Related tables:** audit_event, audit_chain_head, audit_chain_checkpoint, audit_export, legal_hold, security_event, device_limit_violation

**Related business rules:** BR-ADM-08, BR-ADM-09, BR-ADM-10

## ADR-017: No explicit PARTITION BY; scale through range splitting, hash-sharded indexes and TTL; partition names reserved

**Status:** Accepted  |  **Date:** 2026-10-16  |  **Milestones:** B73, B74

**Context.** B73 asks for the partitioning strategy for application and notification tables; rule group 8 requires a stated pattern for partitions.

**Decision.** No table is explicitly partitioned. **Context.** Cross-row invariants (child in the same tenant, state belongs to country, history row follows an allowed transition) cannot use CHECKs across tables and triggers are not relied on.

Examples: job_application -> job_requirement(organisation_id, id); job_application_status_history -> application_status_transition (+ self composite FK chain); city -> state_region(country_id, id); device_session -> device_slot(licence_seat_id, id) and licence_seat(id, app_user_id); gig_assignment -> gig_application(application, request, worker, is_accepted=true); user_block -> block_policy.

**Alternatives considered.** (A) triggers; (B) application checks; (C) wide denormalised columns without FK.

**Reason.** Pure declarative integrity; MATCH SIMPLE skips the check when a part is NULL, which is exploited (first period, city-states) and documented.

**Trade-off.** Referenced tables need extra UNIQUE constraints (index cost); MATCH PARTIAL is unsupported; FK to a partial unique index is impossible; DEFERRABLE FKs are unverified so mutual references use one-directional pointers.

**Consequences.** Tenant pinning needs `uq_<t>_id_organisation_id` on every parent.

**Related tables:** job_application, job_application_status_history, city, state_region, device_session, gig_assignment, user_block, block_policy

## ADR-030: Column and table-width discipline: counters and statistics off hot rows

**Status:** Accepted  |  **Date:** 2026-10-16  |  **Milestones:** B12, B14, B73

**Context.** Wide, hot rows suffer under SERIALIZABLE (contention, retries) and inflate every index that STORINGs them.

**Decision.** Average 14.2 columns per non-lookup table (max 56 on job_requirement; 7 tables > 30 columns; 2 > 40). Counters live in separate stat tables refreshed in batches: job_requirement_stat, community_post_stat, organisation_rating_summary, gig_worker_rating_summary; follower counts are not stored (organisation_follow facts + analytics); large authors' feeds are merged on read. **Reason.** Parent rows stay stable under concurrent updates; stats can be eventually consistent.

**Consequences.** 643 JSONB columns exist; each is for payloads/snapshots/criteria, not for entities that need FKs.

**Related tables:** job_requirement, job_requirement_stat, community_post_stat, organisation_rating_summary, gig_worker_rating_summary, ad_budget_shard, organisation_follow

## ADR-031: Idempotency keys on every integration or money-moving write

**Status:** Accepted  |  **Date:** 2026-10-16  |  **Milestones:** B47, B57, B63

**Context.** Section 6 requires an idempotency answer per boundary; SERIALIZABLE retries (40001) re-run whole transactions.

**Decision.** 19 tables carry a unique *idempotency_key (ad_billing_event, ad_budget_ledger, background_check_order, candidate_identity_verification, employer_branding_purchase, gig_assignment, gig_earnings_snapshot, gig_fulfilment_event ...). Webhooks use UNIQUE(provider, provider_event_ref) / (payment_gateway_id, gateway_event_ref); loads use `INSERT ... ## ADR-032: Isolation and retry policy: SERIALIZABLE everywhere, client retry loop on 40001, FOR UPDATE for ordering

**Status:** Accepted  |  **Date:** 2026-10-16  |  **Milestones:** B45, B47, B79

**Context.** CockroachDB defaults to SERIALIZABLE; READ COMMITTED exists (enabled by default, version of introduction unverified) but allows lost updates and write skew.

**Decision.** All business transactions run SERIALIZABLE. The client wraps every transaction in a retry loop on SQLSTATE 40001 (up to 5 attempts with jittered backoff, BR-LIC-06, BR-SUB-08); single-statement implicit transactions rely on server-side retry. SELECT ... FOR UPDATE is used for ordering contended rows (licence_seat, wallet, audit_chain_head, invoice_number_series, event row for capacity); correctness never depends on it alone.

**Alternatives considered.** (A) READ COMMITTED to avoid retries; (B) advisory locks (session-scoped unsupported); (C) optimistic version columns only.

**Reason.** Serializable plus unique indexes is the simplest proof of the no-overlap and wallet rules; locks make queues short.

**Trade-off.** Lock durability is best-effort under SERIALIZABLE (lost on lease transfer/split/merge -> 40001); `enable_durable_locking_for_serializable` optional; DDL is not fully transactional (XXA00).

**Consequences.** All write paths in the seed generator and the API must implement retries; B79 tests must include concurrent logins and wallet debits.

**Related tables:** licence_seat, wallet, audit_chain_head, invoice_number_series, event, job_application

**Related business rules:** BR-LIC-06, BR-SUB-08

## ADR-033: Naming of physical objects (D-18) and the 63-character index-name deviation

**Status:** Accepted  |  **Date:** 2026-10-16  |  **Milestones:** B16, B20

**Context.** Rule group 1 sets idx_table_column and uq_table_column; rule group 8 requires stated patterns for partitions, views, materialised views and analytics objects.

**Decision.** Tables singular snake_case; analytics tables dim_/fact_/agg_/bridge_ (reserved for the analytics module, lint-enforced); views vw_*; materialised views mv_*; partitions/zones <table>_p_<key>/<table>_zone; indexes idx_<table>_<cols>, uniques uq_<table>_<cols>, FKs fk_<table>_<col>, checks ck_<table>_<what>. Index/constraint names are built from full column lists so names stay unambiguous.

**Trade-off.** 202 index/constraint/FK names exceed 63 characters (longest 121). CockroachDB accepts identifiers up to 128 bytes (`max_identifier_length`, not enforced yet) but stock PostgreSQL truncates at 63: rename before porting (DEV-06). Table names max 37, column names max 39 characters.

## ADR-040: Polymorphic references use one nullable FK per target plus an exactly-one CHECK; *_ref columns are deliberately FK-less

**Status:** Accepted  |  **Date:** 2026-10-16  |  **Milestones:** B22, B33, B59

**Context.** Several rows point to one of many tables (certificate source, learning assignment target, ledger reference, audit entity). An untyped (type, id) pair cannot be an enforced FK (Rule 2).

**Decision.** Where the target set is small and stable, one nullable FK per target type and a CHECK that exactly one is set (num_nonnulls or (a IS NULL) <> (b IS NULL)): wallet_ledger_entry (ck_wallet_ledger_entry_single_reference), candidate_project, gig_slot. Where the target set is open or must outlive the row (audit_event.entity_ref, notification source_object_ref, analytics source ids), a 155-column family of `*_ref` columns is intentionally not an FK and is paired with a type code; the lint treats `*_id` without FK as an error but `*_ref` as allowed.

**Alternatives considered.** (A) polymorphic type+id everywhere; (B) a join table per target.

**Reason.** Keeps every `*_id` enforced while allowing durable, cheap log references.

**Trade-off.** `*_ref` columns can dangle; the nightly orphan check job covers them. `num_nonnulls` is avoided in ext_talent_ops because it is unverified in CockroachDB docs.

**Consequences.** 07 lists the FK-less reference families as a Section 5 deviation.

**Related tables:** wallet_ledger_entry, candidate_project, gig_slot, audit_event, notification, candidate_activity_log

## ADR-042: Append-only is enforced by privileges AND a row trigger; TTL and purge are the only deleters

**Status:** Accepted  |  **Date:** 2026-10-16  |  **Milestones:** B79, B58

**Context.** BR-ADM-08 and the RBAC matrix (GR-14) make 125 tables append-only by granting INSERT/SELECT only. Verification on the real v26.2.8 cluster (docs/crdb_smoke_results.md) showed that owner and admin bypass REVOKE, that row-level TTL deletes and FK ON DELETE CASCADE both fire row triggers, and that a plain always-raising trigger therefore makes the TTL job fail.

**Decision.** Every append_only table has `trg_<table>_append_only BEFORE UPDATE OR DELETE FOR EACH ROW` (SQLSTATE 42501) in addition to the missing UPDATE/DELETE grants. UPDATE is always blocked. DELETE is allowed only (a) for rows already past their TTL expiry (tables with a TTL get a per-table function `fn_ao_<table>` using the same expression as the TTL) or (b) inside a purge run: current_user is a member of purge_svc AND `SET app.purge_run_id` is non-empty (`fn_is_purge_run()`), which lets retention/erasure cascades from a hard-deleted parent through. Everyone else, including the table owner and root, is blocked.

**Alternatives considered.** (A) privileges only (bypassed by owner/admin); (B) trigger that always raises (breaks TTL and cascades, proven on the cluster); (C) no TTL on append-only tables (violates retention rules).

**Reason.** Defence in depth that survives a later wide GRANT or an operator mistake, and keeps retention working. The TTL job and purge_svc keep the documented behaviour.

**Trade-off.** Two extra functions per TTL table (42 tables); purge_svc must set app.purge_run_id and write purge_job_run; trigger cost applies only to UPDATE/DELETE, not INSERT.

**Consequences.** TRUNCATE is still possible for the owner/admin: owner is the NOLOGIN schema_owner (E-27). Tests: tests/test_catalog_conformance.py (append-only section), tests/test_rules_money.py.

**Related tables:** audit_event, wallet_ledger_entry, user_credential_history

**Related business rules:** BR-ADM-08
